# 3.4 Conectividade e Comunicação

## Tecnologia de Conectividade Escolhida: Wi-Fi

O projeto utiliza a interface Wi-Fi 802.11 b/g/n (2,4 GHz) nativa do ESP32, operando em **modo estação (Station Mode / STA)** — ou seja, o ESP32 se conecta como cliente a uma rede já existente, em vez de criar sua própria rede (modo Access Point). A associação à rede é feita via protocolo de segurança **WPA2-PSK**, o padrão suportado por praticamente qualquer roteador doméstico ou de escola, e o endereço IP do dispositivo na rede local é obtido automaticamente por **DHCP**, dispensando qualquer configuração manual de rede no dia da demonstração. No dia da Feira EPA, essa rede será fornecida/distribuída pelo próprio professor especificamente para o grupo.

Essa camada é responsável por manter a conexão lógica sobre o rádio físico usada quando o ESP32 atua como **servidor**, aceitando requisições HTTP de outros dispositivos da mesma rede local — em especial, do dashboard que consome os dados dos três postes. O SoC ESP32 gerencia essa função através da pilha TCP/IP (**lwIP**) embutida no seu SDK, que permite abrir sockets e atender múltiplas requisições sem necessidade de hardware adicional.

A escolha do Wi-Fi em detrimento das demais opções se justifica tecnicamente:

- **Frente a Bluetooth (HC-05/06):** o Bluetooth clássico não possui pilha IP própria — ele exigiria um dispositivo intermediário (como um smartphone) atuando como ponte, o que inviabilizaria o ESP32 funcionar como um servidor HTTP acessível diretamente pela rede local;
- **Frente a LoRa (SX1278):** o LoRa opera com taxas de transmissão muito baixas (tipicamente entre 0,3 e 50 kbps) e não é orientado a IP — ele é ideal para telemetria de longuíssimo alcance com poucos bytes por transmissão, o que não corresponde à necessidade do projeto de servir requisições HTTP estruturadas para o dashboard;
- **Frente a GSM/GPRS (SIM800L):** apesar de resolver o problema de alcance via rede celular, o módulo exigiria um chip SIM ativo com plano de dados, custo recorrente mensal e uma antena externa — despesas incompatíveis com a proposta de solução de baixo custo do projeto, para um cenário (maquete estacionária, numa rede local já disponível) em que isso não traz benefício real.

Em termos de desempenho, a interface Wi-Fi do ESP32 alcança taxas de transmissão de até 150 Mbps (802.11n), muito acima do necessário para o volume de dados do projeto — cada requisição carrega poucos kilobytes (o JSON de status dos três postes, servido pelo próprio ESP32 ao dashboard), de modo que a latência de rede não é um fator crítico de projeto.

## Protocolo de Comunicação Escolhido: HTTP

O sistema utiliza um **servidor HTTP embutido no próprio ESP32**, rodando na porta 80 através da biblioteca `WebServer.h`. Ao receber uma requisição `GET` na rota `/api/status`, o servidor monta e retorna uma resposta em JSON com o estado atual dos três postes (leitura de cada LDR, se o slide switch daquele poste está simulando falha, e o estado do LED correspondente). O dashboard, rodando em outro dispositivo da mesma rede Wi-Fi, faz requisições periódicas a esse endereço para manter a exibição atualizada. Essa implementação (Wi-Fi + servidor local) foi conduzida por Rafael Alves, com apoio técnico de Victor Eufrásio.

Comparando com as alternativas do enunciado: o **MQTT** é otimizado para o padrão publish/subscribe, no qual múltiplos dispositivos publicam continuamente pequenas mensagens de telemetria para um broker central que redistribui aos interessados — um modelo vantajoso em escala (dezenas/centenas de sensores), mas que, para os três postes de um único nó ESP32 atuando como seu próprio servidor, adicionaria uma peça de infraestrutura (o broker) sem ganho real de desempenho. O **WebSocket**, por sua vez, resolveria uma limitação real do HTTP tradicional: como o protocolo HTTP é do tipo requisição-resposta, o dashboard só se atualiza quando faz uma nova requisição (manualmente, ou por um `polling` automático via JavaScript); o WebSocket manteria uma conexão persistente e bidirecional, permitindo que o ESP32 empurrasse atualizações de status para o dashboard em tempo real, sem a necessidade de repetir a requisição. Essa é registrada como uma melhoria técnica viável para trabalhos futuros, mas o HTTP com atualização periódica é suficiente para os objetivos de demonstração do projeto atual. Já o protocolo **Serial** não se aplica ao escopo, por não existir, no projeto, comunicação direta por fio entre dois dispositivos processadores distintos.

## Integração das Camadas

A conectividade (Wi-Fi) e a comunicação (HTTP) atuam de forma conjunta e dependente: o Wi-Fi fornece o meio físico de acesso à rede local, enquanto o HTTP define a forma como as mensagens são estruturadas e trafegam sobre esse meio. Na prática, o fluxo funciona assim: o firmware lê continuamente os três LDRs e o estado dos três slide switches, decide localmente (comparando cada leitura ao `LIMIAR_LUZ` e invertendo a decisão quando o switch daquele poste indica falha simulada) o estado de cada poste, e mantém essas informações disponíveis através do servidor HTTP embutido no ESP32; o dashboard, rodando em outro dispositivo da mesma rede Wi-Fi, consulta periodicamente o endpoint `/api/status` e exibe o estado atualizado dos três postes ao público. Toda essa troca acontece dentro da rede local fornecida no dia da apresentação, sem qualquer dependência de servidores externos.
