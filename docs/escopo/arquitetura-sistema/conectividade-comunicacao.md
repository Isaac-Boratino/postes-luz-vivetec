# 3.4 Conectividade e Comunicação

## Tecnologia de Conectividade Escolhida: Wi-Fi

O projeto utiliza a interface Wi-Fi 802.11 b/g/n (2,4 GHz) nativa do ESP32, operando em **modo estação (Station Mode / STA)** — ou seja, o ESP32 se conecta como cliente a um roteador já existente, em vez de criar sua própria rede (modo Access Point). A associação à rede é feita via protocolo de segurança **WPA2-PSK**, o padrão suportado por praticamente qualquer roteador doméstico ou de escola, e o endereço IP do dispositivo na rede local é obtido automaticamente por **DHCP**, dispensando qualquer configuração manual de rede no dia da demonstração.

Essa camada é responsável por manter conexões lógicas simultâneas sobre o mesmo rádio físico: conexões **de saída**, usadas quando o ESP32 atua como cliente para contatar servidores externos (API do Telegram, API do ThingSpeak, servidor NTP), e uma conexão **de entrada**, usada quando o próprio ESP32 atua como servidor, aceitando requisições de outros dispositivos da rede local que queiram acessar o painel web. O SoC ESP32 gerencia essas funções através da pilha TCP/IP (**lwIP**) embutida no seu SDK, que permite abrir múltiplos sockets simultâneos sem necessidade de hardware adicional.

A escolha do Wi-Fi em detrimento das demais opções se justifica tecnicamente:

- **Frente a Bluetooth (HC-05/06):** o Bluetooth clássico não possui pilha IP própria — ele exigiria um dispositivo intermediário (como um smartphone) atuando como ponte entre o ESP32 e a internet, o que adicionaria uma camada de complexidade e um ponto de falha extra, inviabilizando o envio direto de alertas e dados para serviços externos;
- **Frente a LoRa (SX1278):** o LoRa opera com taxas de transmissão muito baixas (tipicamente entre 0,3 e 50 kbps) e não é orientado a IP — ele é ideal para telemetria de longuíssimo alcance com poucos bytes por transmissão, o que não corresponde à necessidade do projeto de enviar requisições HTTP/HTTPS estruturadas e servir páginas HTML completas;
- **Frente a GSM/GPRS (SIM800L):** apesar de resolver o problema de alcance via rede celular, o módulo exigiria um chip SIM ativo com plano de dados, custo recorrente mensal e uma antena externa — despesas incompatíveis com a proposta de solução de baixo custo do projeto, para um cenário (maquete estacionária) em que já existe Wi-Fi disponível.

Em termos de desempenho, a interface Wi-Fi do ESP32 alcança taxas de transmissão de até 150 Mbps (802.11n), muito acima do necessário para o volume de dados do projeto — cada requisição carrega poucos kilobytes (uma mensagem de texto para o Telegram, os valores numéricos enviados ao ThingSpeak, ou uma página HTML simples para o painel), de modo que a latência de rede não é um fator crítico de projeto.

## Protocolo de Comunicação Escolhido: HTTP/HTTPS

O sistema utiliza o protocolo HTTP/HTTPS em três frentes complementares, com naturezas técnicas distintas.

**Frente 1 — Cliente HTTPS para a API do Telegram (alerta).** Quando uma falha é detectada, o ESP32 monta uma requisição do tipo `GET` ou `POST` para o endpoint `https://api.telegram.org/bot<TOKEN>/sendMessage`, informando o `chat_id` do grupo/canal de destino e o texto do alerta como parâmetros. Como esse endereço opera sobre a porta 443 com criptografia TLS, o firmware precisa estabelecer a conexão através da classe `WiFiClientSecure` (em vez do `WiFiClient` simples usado para HTTP puro), responsável por negociar o handshake TLS antes de enviar os dados. Isso é feito, na prática, com bibliotecas de mais alto nível já preparadas para isso — como a `UniversalTelegramBot` — que empacotam a lógica de formatação da requisição, o tratamento da resposta em JSON e a gestão da conexão segura. Esse é o canal que simula, na maquete, a notificação enviada a um responsável pela manutenção.

**Frente 2 — Cliente HTTP para a API do ThingSpeak (histórico).** Periodicamente (respeitando o intervalo mínimo de 15 segundos entre gravações do plano gratuito), o ESP32 monta uma requisição `GET` para o endpoint `https://api.thingspeak.com/update`, informando a **Write API Key** do canal e os valores lidos de cada um dos três LDRs como campos (`field1`, `field2`, `field3`). Essa comunicação pode ser feita com a biblioteca oficial `ThingSpeak.h` (da MathWorks), que encapsula a montagem da requisição e o tratamento da resposta.

**Frente 3 — Servidor HTTP local (painel web).** Paralelamente às duas frentes anteriores, o ESP32 instancia um servidor HTTP na porta 80 (via biblioteca `WebServer.h`), que fica escutando requisições de qualquer navegador conectado à mesma rede Wi-Fi. Ao receber uma requisição `GET` na rota raiz (`/`), o servidor monta e retorna uma resposta HTML/CSS gerada dinamicamente a partir das variáveis de estado dos três postes (lidas dos LDRs), permitindo que o painel sempre reflita o status mais recente sem exigir reinicialização ou reconfiguração.

Comparando com as alternativas do enunciado: o **MQTT** é otimizado para o padrão publish/subscribe, no qual múltiplos dispositivos publicam continuamente pequenas mensagens de telemetria para um broker central que redistribui aos interessados — um modelo vantajoso em escala (dezenas/centenas de sensores), mas que, para os três postes de um único nó ESP32 sem necessidade de broker dedicado, adicionaria uma peça de infraestrutura sem ganho real de desempenho (o próprio ThingSpeak, inclusive, aceita publicação via MQTT como alternativa ao HTTP, mas a via HTTP é mais simples de implementar e depurar num projeto acadêmico). O **WebSocket**, por sua vez, resolveria uma limitação real do HTTP tradicional: como o protocolo HTTP é do tipo requisição-resposta, o painel web só se atualiza quando o navegador solicita a página novamente (manualmente, ou via `refresh` automático por JavaScript); o WebSocket manteria uma conexão persistente e bidirecional, permitindo que o ESP32 empurrasse atualizações de status para o navegador em tempo real, sem a necessidade de recarregamento. Essa é registrada como uma melhoria técnica viável para trabalhos futuros, mas o HTTP com atualização periódica é suficiente para os objetivos de demonstração do projeto atual. Já o protocolo **Serial** não se aplica ao escopo, por não existir, no projeto, comunicação direta por fio entre dois dispositivos processadores distintos.

## Sincronização de Horário via NTP

Uma quarta comunicação, de menor volume mas igualmente essencial, ocorre sobre a mesma conexão Wi-Fi: a sincronização de horário via **NTP (Network Time Protocol)**, que roda sobre a porta UDP 123 e é usada pelo ESP32 para consultar servidores públicos de tempo (como os do `pool.ntp.org`). Diferente do HTTP, o NTP é um protocolo leve, de requisição única e resposta compacta, adequado para uma consulta esporádica de horário em vez de uma troca contínua de dados. É esse horário sincronizado que alimenta a lógica condicional central do firmware — comparar se é dia ou noite para decidir se o estado de um poste (aceso/apagado) representa uma falha ou um funcionamento normal — e por isso a exatidão dessa sincronização é um requisito técnico tão importante quanto o próprio envio do alerta.

## Integração das Camadas

A conectividade (Wi-Fi) e a comunicação (HTTP/HTTPS) atuam de forma conjunta e dependente: o Wi-Fi fornece o meio físico de acesso à rede, enquanto o HTTP/HTTPS define a forma como as mensagens são estruturadas e trafegam sobre esse meio. Na prática, quando o ESP32 identifica uma falha em um poste, ele monta uma requisição HTTPS para a API do Telegram através da conexão Wi-Fi já estabelecida, disparando o alerta pontual; em paralelo, e de forma independente desse evento, ele envia periodicamente os valores de luminosidade ao ThingSpeak, construindo o histórico em forma de gráfico; e, simultaneamente a tudo isso, o mesmo módulo Wi-Fi mantém o servidor HTTP local ativo, pronto para responder a qualquer dispositivo da rede que acesse o painel pelo navegador. Essa combinação cobre três necessidades complementares: notificação ativa (Telegram), registro histórico (ThingSpeak) e consulta imediata sob demanda (painel web) — sem que uma dependa do funcionamento das outras.
