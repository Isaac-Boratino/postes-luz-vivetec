# 3.5 Plataforma IoT / Armazenamento

## Plataforma Escolhida: ThingSpeak

O projeto utiliza o **ThingSpeak** (plataforma de IoT mantida pela MathWorks, mesma empresa do MATLAB) como camada de armazenamento e visualização histórica dos dados de luminosidade captados pelos três sensores LDR. A escolha se justifica por três motivos alinhados diretamente às necessidades do projeto:

**1. Estrutura de canais e campos compatível com o cenário do projeto.** O ThingSpeak organiza os dados em "canais", cada um com até 8 "campos" (fields) numéricos independentes. Isso se encaixa perfeitamente na necessidade de monitorar três postes simultaneamente: cada LDR é mapeado para um campo distinto do mesmo canal (`field1`, `field2`, `field3`), permitindo acompanhar o comportamento de cada poste de forma individual, mas dentro de uma única estrutura de dados.

**2. Geração automática de gráficos.** Diferente de uma solução de armazenamento "cru" (como um banco de dados genérico), o ThingSpeak gera automaticamente gráficos de linha do tempo para cada campo assim que os dados são recebidos, sem necessidade de programação adicional no lado do servidor. Isso é especialmente relevante para o objetivo de "apresentar o funcionamento do sistema de forma clara na Feira EPA": em vez de depender apenas do estado momentâneo mostrado no painel local, o projeto ganha uma evidência visual do padrão de acender/apagar dos postes ao longo do tempo, reforçando a lógica de comparação dia/noite que sustenta todo o sistema.

**3. Integração simples e de baixo custo.** O plano gratuito do ThingSpeak permite até 3 milhões de mensagens por ano (mais do que suficiente para uma demonstração pontual) e é acessado por uma API REST simples via HTTP, sem necessidade de bibliotecas complexas ou configuração de servidor próprio. Existe ainda uma biblioteca oficial (`ThingSpeak.h`) mantida pela própria MathWorks e compatível com o ambiente Arduino/ESP32, o que reduz o tempo de desenvolvimento.

## Comparação com as Demais Opções

- **Adafruit IO:** também oferece dashboards e feeds gratuitos, e seria uma alternativa viável; porém, o ThingSpeak tem uma curva de aprendizado mais direta para o caso específico de poucos campos numéricos com foco em gráficos de série temporal, que é exatamente o que o projeto precisa.
- **Blynk:** é voltado principalmente para controle e visualização via aplicativo mobile personalizável, com foco maior em interação/controle do que em histórico gráfico — o projeto já resolve a parte de consulta imediata com o painel web embutido no ESP32, então o diferencial do Blynk não agrega tanto quanto o histórico gráfico do ThingSpeak.
- **Firebase:** é um banco de dados em tempo real completo, poderoso, mas exige mais configuração (criação de projeto no console do Google, regras de segurança, SDKs) para um ganho que, na escala deste projeto (três sensores, um evento de demonstração), não compensa a complexidade adicional.
- **MQTT Broker próprio (Mosquitto):** exigiria um segundo dispositivo (como um Raspberry Pi) hospedando o broker, o que aumenta custo, complexidade de montagem e pontos de falha — incompatível com a proposta de solução simples e de baixo custo do projeto.
- **Ubidots:** tem um plano educacional gratuito interessante e também seria funcional, mas com menos documentação em português e exemplos prontos para ESP32 do que o ThingSpeak, o que pesa em um projeto com prazo definido.

## Bot do Telegram — Detalhamento Técnico

**Criação e autenticação do bot.** O bot é criado gratuitamente através do **BotFather**, um bot oficial do próprio Telegram usado para registrar novos bots e gerar o **token de acesso** (uma string única que identifica e autentica o bot perante a API). Esse token deve ser mantido em segredo no firmware, já que qualquer pessoa que o possua pode enviar mensagens em nome do bot. Além do token, é necessário obter o **`chat_id`** do grupo, canal ou conversa individual para onde os alertas serão enviados — um identificador numérico único que pode ser descoberto enviando uma mensagem ao bot e consultando o endpoint `getUpdates` da API uma única vez, durante a configuração inicial.

**Envio da mensagem (sem necessidade de polling).** Diferente de bots que precisam reagir a comandos do usuário (o que exigiria consultar continuamente o endpoint `getUpdates`, técnica chamada *long polling*), este projeto usa o bot apenas no sentido de saída: o ESP32 só **envia** mensagens, nunca precisa **receber** comandos. Isso simplifica bastante a implementação, pois dispensa manter uma rotina de verificação constante — o firmware apenas monta e envia uma requisição ao endpoint `sendMessage` no momento exato em que uma falha é detectada.

**Estrutura técnica da requisição.** A chamada é feita para `https://api.telegram.org/bot<TOKEN>/sendMessage`, sobre TLS (porta 443), exigindo o uso da classe `WiFiClientSecure` no lugar do `WiFiClient` simples. Como o ESP32 tem recursos de memória limitados para armazenar uma cadeia completa de certificados, a prática comum em projetos desse porte é usar `setInsecure()` no cliente seguro (aceitando a conexão sem validar a cadeia de certificados) ou fixar o certificado raiz do Telegram diretamente no código — a biblioteca `UniversalTelegramBot`, amplamente usada para esse fim, já abstrai essa escolha e cuida do encapsulamento da mensagem em formato compatível com a API (incluindo o `chat_id` e o texto formatado). O corpo da mensagem é montado dinamicamente no firmware, concatenando o identificador do poste, a localização simulada e o horário (obtido via NTP), no formato já usado como exemplo no bloco de arquitetura do sistema.

**Limites de uso.** A API do Telegram impõe limites de taxa de envio (rate limits) — cerca de 30 mensagens por segundo no agregado da API e cerca de 1 mensagem por segundo por chat individual — limites muito acima do volume gerado por este projeto (uma mensagem pontual por evento de falha), então não representam uma restrição prática.

## Painel Web Local — Detalhamento Técnico

**Biblioteca e inicialização do servidor.** O painel é implementado com a biblioteca `WebServer.h` (nativa do core ESP32 para Arduino), que instancia um servidor HTTP na porta 80. Após a conexão à rede Wi-Fi, o firmware registra rotas específicas com o método `server.on(rota, funçãoDeResposta)` — tipicamente uma rota raiz (`/`) que retorna a página principal do painel — e inicia o servidor com `server.begin()`. A partir daí, o loop principal do firmware precisa chamar `server.handleClient()` repetidamente, responsável por verificar e atender requisições recebidas sem bloquear as demais tarefas do sistema (leitura dos sensores, envio ao ThingSpeak, verificação de falhas).

**Geração dinâmica do conteúdo.** A página HTML não fica armazenada como um arquivo estático: ela é montada em tempo de execução, concatenando strings de HTML/CSS com os valores atuais do estado de cada poste (obtidos das variáveis internas do firmware, atualizadas a cada ciclo de leitura dos LDRs). Para economizar a memória RAM limitada do ESP32, é comum armazenar os trechos fixos do HTML na memória de programa (Flash), usando a macro `PROGMEM` ou literais `F("...")`, em vez de mantê-los como strings comuns ocupando RAM durante toda a execução.

**Acesso ao painel.** Como o ESP32 opera em modo estação (conectado a um roteador existente, e não criando sua própria rede), o endereço IP atribuído por DHCP não é fixo por padrão — por isso, o firmware normalmente imprime esse IP na porta serial durante a inicialização (útil durante o desenvolvimento) e pode, opcionalmente, registrar um nome de host amigável na rede local via **mDNS** (biblioteca `ESPmDNS`), permitindo acessar o painel por um endereço como `http://postes.local` em vez do IP numérico — o que facilita a demonstração na Feira EPA sem depender de descobrir o IP a cada nova conexão.

**Atualização do conteúdo.** Como o HTTP é um protocolo de requisição-resposta (o servidor só responde quando solicitado), o painel reflete o estado mais recente apenas quando a página é carregada ou recarregada — por padrão, isso pode ser feito manualmente pelo usuário ou automatizado com uma tag `<meta http-equiv="refresh" content="5">` no HTML gerado, fazendo o navegador recarregar a página a cada poucos segundos. Essa é a limitação que a melhoria futura com WebSocket (mencionada na seção de Conectividade e Comunicação) resolveria de forma mais elegante, eliminando a necessidade de recarregamento.

## Fluxo de Dados na Plataforma

O ciclo de armazenamento funciona da seguinte forma: em intervalos regulares (respeitando o limite mínimo de 15 segundos entre gravações do plano gratuito), o firmware do ESP32 lê os três canais ADC1 correspondentes aos LDRs, converte essas leituras nos valores que serão enviados, e realiza uma requisição HTTP `GET` para o endpoint `https://api.thingspeak.com/update`, informando a **Write API Key** do canal (chave que identifica e autoriza a escrita naquele canal específico) e os três valores como parâmetros (`field1=`, `field2=`, `field3=`). O ThingSpeak recebe essa requisição, armazena o registro com um timestamp automático, e atualiza os gráficos do canal em tempo real — que podem então ser visualizados publicamente ou de forma privada, conforme a configuração escolhida para o canal, em qualquer navegador com acesso à internet, inclusive durante a apresentação na Feira EPA.

Esse fluxo é independente do alerta enviado via Telegram e da exibição no painel web local: os três funcionam em paralelo, cada um atendendo a uma necessidade distinta do projeto — notificação pontual, consulta imediata e histórico de longo prazo, respectivamente.
